## 3. Разбор граничных случаев (п. 8 контракта)

- **Симметрия sign/verify:** sign пишет ровно 32 пары (a, b) на 32 байта SHA-256 (`:179-183`); verify читает ровно 32 пары + контроль EOF для detached; для attached после 512-байтного префикса остаток хешируется потоком. Асимметрий нет.
- **Пустой файл:** SHA-256 пустого входа — 32 байта → 32 пары → 512 байт; `verifyAttached` файла ровно 512 байт: `digestRemaining` возвращает дайджест пустого остатка — корректно в обе стороны.
- **h = 0 / b = 0:** цикл `while (b == 0)` (`:190-194`) пересчитывает k, a и b вместе, как требует контракт («пересчитать пару»); счётчик не нужен (вероятность ~1/(p−1)).
- **Корректность инверсии k:** `modInverse(k, p−1)` безопасен — k допущен только с `gcdSimple(k, p−1) == 1` (`:210`); `longValueExact` не переполнится (результат < p−1 ≤ 3 036 999 999).
- **Завершимость повтора k:** при чётном p−1 обратимы только нечётные k; `nextLong(1, p−1)` накрывает [1, p−2] целиком, доля взаимно простых φ(p−1)/(p−2) > 0 → геометрическое распределение, зацикливание практически исключено. Идентично устоявшемуся `IlGamal.randomSessionKey`.
- **Переполнения:** единственный `%` над произведением — `:255`, оба операнда < p ≤ 3_037_000_000 → произведение < 2^63 (расчёт в п. 2.3); `pow` внутри использует те же границы (a² < p², тот же аргумент, что во всём репозитории); `%` на `:271,:276` — пробное деление положительных. Java `%` на отрицательных не применяется нигде (grep).
- **Ресурсы:** все потоки в try-with-resources — `:78, :102-103, :131, :157, :310`; в `signAttached` reader и writer в одном блоке (`:102-103`), как `RSASign.java:75-79`.
- **Обработка исключений:** идентична `RSASign` (тот же тройной catch, те же английские сообщения «Signing file {} …», «File signed successfully: {}», «Signature is {} valid/invalid» — `:76,:82,:433`).
- **Отсутствующий файл:** `Files.newInputStream` → `NoSuchFileException` (подкласс IOException) — поведение под будущие тесты T3 корректно.
