## 3. Корректность подхода к рандомизированной подписи

- **Бинарное сравнение вывода `sign` с эталоном отсутствует** — правильно (подпись рандомизирована). Вместо него: размер 512 (`:135`), round-trip (`:136`), и независимая проверка уравнения `:176-183` — пары (a, b) читаются из файла и проверяются против SHA-256, посчитанного тестом самостоятельно (`sha256`, `:604-610`), без использования внутренностей `ElGamal`.
- **Детерминированный хелпер** `expectedSignature` (`:536-552`) проверен по математике:
  - k=25: gcd(25, 1008)=1 — обратимость k mod (p−1) гарантирована ⇒ валидная подпись по построению не может быть случайно отвергнута (уравнение g^h ≡ Db^a·a^b выполняется тождественно: Db^a·a^b = g^(Cb·a + k·b), а k·b ≡ h − Cb·a (mod p−1)).
  - Шаг `nextSessionKey` (`:570-577`): 25 → 27 (gcd=9, пропускается) → 29 (gcd=1) — проверено численно; полный пересчёт всех пар при b=0 через `hasZeroCoefficient` (`:579-587`) соответствует контракту плана.
  - `BigInteger.modInverse`/`.mod` (`:559-562`) — floorMod-семантика, Java `%` для отрицательных не используется. Зеркало продакшн-кода (`ElGamal.java:199-206`).
  - Endianness: тестовый `writeLong` (`:589-593`) — 8 байт big-endian, порядок «a, затем b» (`:547-548`) — побайтово совпадает с продакшеном (`ElGamal.java:335-339`, `:181-182`); `readLong` (`:595-602`) зеркален продакшену.
  - Диапазоны валидны по построению: a = g^k mod p ∈ [1, 1008], b ∈ [0, 1007] — проходит range-check `ElGamal.java:238`.
- **Независимая верификация чисел** (мой расчёт вне тестового кода): 11 — первообразный корень 1009 (факторы 1008 = 2·2·2·2·3·3·7, все проверки ≠ 1); 2 — НЕ первообразный корень (негативная строка `:216` реально попадает в reject-ветку, не «случайно проходит»); Db = 11^168 mod 1009 = 375 — согласуется с `@CsvSource` `:360,363`; a(k=25) = 776.

## 4. Качество ассертов (нет таутологий, негативы доказуемы)

- **«Чужой ключ»** (`:347-356`, sign с Cb+1, verify с Db): уравнение после подстановки сводится к g^h ≡ g^(h−a), т.е. требует 11^a ≡ 1 (mod 1009) при a ∈ [1, 1007] — проверено исчерпывающе, таких a нет ⇒ **ложь гарантирована для любого случайного k**, не «случайно false».
- **Флип последнего лонга подписи** (`:341`): b → b±1 держит уравнение только при a ≡ 1 (mod p), что для a = g^k, k ∈ [1, 1007], невозможно ⇒ доказуемо false.
- **Флип последнего байта данных** (`:458`) и модификации файла (`:407-414`): для фиксированной пары уравнение эквивалентно h′ ≡ h (mod 1008), а байты SHA-256 лежат в [0, 255] ⊂ [0, 1007] ⇒ любое изменение хеша обнаруживается детерминированно.
- **Невалидные a/b** (`:397-424`, хелпер `:529-534`) попадают точно в range-check `ElGamal.java:238` (a=0/−1 < 1; b=1008/1009 > 1007; b=−1 < 0; кодировка 8B BE с обратной стороной согласована) — детерминированно, через детерминированный хелпер.

Примечание: в плане (lab-9.md:64) байт 7 назван «b первой пары» — фактически a занимает байты 0–7; на осмысленность флипа не влияет (информационно).
